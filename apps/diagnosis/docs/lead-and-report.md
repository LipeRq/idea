# PDFレポートと無料相談の申し込み:設計

診断の結果画面から「PDFをダウンロード」と「無料相談の申し込み」ができる。どちらも、クライアントから送られた結果をそのまま信用せず、サーバーで入力から計算し直す。

## PDFレポート

### 方式:サーバーで生成(@react-pdf/renderer + Noto Sans JP 同梱)

`POST /api/report` が PDF を作って返す。結果画面のボタンは、診断に使った入力(とAIの文章・署名)を送り、返ってきた PDF をファイルとして保存させる。

| 検討した方式 | 判断 |
|---|---|
| 印刷用CSSの改善(`window.print()`) | ブラウザごとに余白・改ページ・ヘッダーが変わり、「保存」までの操作も利用者任せになる。ブランドの整った成果物にならないので、補助(「印刷する」ボタン)として残すだけにした |
| ヘッドレスブラウザで印刷 | サーバーにChromiumが必要で重い。サーバーレスで動かしにくい |
| **@react-pdf/renderer** | Node だけで動き、レイアウトを React で書ける。フォントは使った字だけを埋め込む(PDFは100KB前後)。Next.js が自動でバンドル対象外にするパッケージなので設定も少ない |

- **日本語フォント**:Noto Sans JP(Regular / Bold、v2.004、SIL Open Font License 1.1)を `assets/fonts/` に同梱し、ライセンス全文を `assets/fonts/OFL.txt` に置いた。ファイルは Google Fonts 配布の静的TTFを加工せずに使っている(GitHub から取得できない環境だったため、同じファイルを収録した npm パッケージ `@expo-google-fonts/noto-sans-jp@0.4.4` から取り出した)。髙・﨑などの人名用の字も入っている。
- **日本語の改行**:react-pdf は空白でしか改行しないため、`src/lib/report/line-break.ts` で文字単位の改行位置を渡している。句読点・閉じ括弧・小書きの仮名は行頭に、開き括弧は行末に来ないようにし、「216万円」「AI-OCR」のような数字と単位・英単語は分けない。
- **内容**:表紙ページに年間削減見込み額・準備度・費用の目安・総評・業務別の削減見込み額のグラフ、続いて優先施策(5件)、3ヶ月のロードマップ、準備度の内訳と導入前に整えたいこと、試算の内訳と前提(計算式・実現係数・人件費・費用の目安)、注意書き、あわせて使えるツール(当てはまるときだけ。結果画面と同じルールで選び、リンクはURLが設定されているものだけ。README の「関連ツールの案内」)、専門家と深掘りしたいポイントと申し込み先。各ページのフッターに「試算は概算であり、効果を保証するものではありません」とページ番号を入れる。
- **フォントの読み込み**:実行時にファイルから読むので、`next.config.ts` の `outputFileTracingIncludes` で本番のサーバーにも含める。

### 改ざんされても困らない設計

- **数値**:送られてきた `result` は使わない(スキーマで捨てる)。`input` を診断と同じスキーマで検証し、`calculateDiagnosis` で計算し直す。数値を書き換えた PDF を作ることはできない。
- **AIの文章**:作り直すとAIの呼び出しが毎回かかり、内容も変わる。そこで、診断のときにサーバーが「入力+AIの文章」に HMAC-SHA256 の署名(24時間有効、`REPORT_SIGNING_SECRET`)を付けて返し、PDF を作るときに署名が一致した場合だけAIの文章を使う。一致しなければ(書き換え・期限切れ・署名なし)、計算結果から作る標準文面にする。利用者が自社名の入った PDF の文言(例:「効果を保証します」)を自由に書き換えて配ることはできない。
- 会社名や課題など利用者が入力した文字は、そのまま文字として描くだけ(リンクやHTMLにはしない)。
- `REPORT_SIGNING_SECRET` が未設定のときはプロセスごとの乱数を使う。1台で動かすなら問題ないが、複数インスタンスや再起動をまたぐと検証に失敗し、AIの文章の代わりに標準文面になる(数値は同じ)。本番では設定する。

## 無料相談の申し込み

### 流れ

結果画面のフォーム(会社名・氏名・メール・電話(任意)・相談したい内容・個人情報の取り扱いへの同意。関連ツールを案内したときは「相談したいテーマ」も出し、選ぶと相談したい内容の欄に入る)→ `POST /api/lead` → 設定された送信先へ。

- 入力の検証は画面とサーバーで同じ zod スキーマ(`src/lib/lead/schema.ts`)を使う。サーバーは欄ごとのエラーを返し、画面はその欄に表示する。
- 診断結果の要約(業種、従業員規模、年間削減見込み額、準備度、優先施策の上位3件)は、送られた `input` からサーバーで計算し直して添える。

### 送信先(アダプター方式)

`src/lib/lead/deliver.ts` が環境変数を見て送信先を選ぶ。両方設定すれば両方に送り、1つでも届けば成功とする(例:Salesforce にリードを作り、Slack で気づく)。

| 送信先 | 有効になる条件 | 内容 |
|---|---|---|
| Salesforce Web-to-Lead | `SALESFORCE_ORG_ID` | 標準項目(姓・会社名・メール・電話・説明・リードソース)に入れる。診断の各値は `SALESFORCE_FIELD_MAP` でカスタム項目に対応付けられる |
| Webhook | `LEAD_WEBHOOK_URL` | Slack の Incoming Webhook なら本文(text)、それ以外は項目ごとのJSON。`LEAD_WEBHOOK_SECRET` で本文の署名を付けられる |
| サーバーログ(開発用) | どちらも未設定で、開発時か `LEAD_LOG_ONLY=true` | 個人情報は伏せて(先頭1文字と文字数だけ)出す |

- Web-to-Lead を選んだのは、APIの認証情報(接続アプリケーションやトークン)をこのアプリに置かずに済み、Salesforce 側の設定だけでリードの割り当てルールや自動返信が使えるため。ただし Web-to-Lead は取り込みに失敗しても HTTP 200 を返すことがあるので、確実に届いたかは Salesforce 側で確認する(`SALESFORCE_DEBUG_EMAIL` で受信内容のメールを受け取れる)。1日の上限(既定500件)もある。
- 本番で送信先が未設定のときは、申し込みを捨てないよう 503 を返して画面に「受け付けられません」と出す(ログに出すだけで受け付けたことにすると、申し込みが誰にも届かないまま失われる)。

### スパム・乱用対策

- ハニーポット:画面外に置いた、読み上げとキーボード操作の対象外の欄(`website`)。入力があればボットとみなし、送ったふりをして(200)捨てる。
- 本文の大きさ:32KBを超えたら読まずに 413。各欄にも文字数の上限。
- 回数制限:送信元ごとに1時間5回(`RATE_LIMIT_LEAD_PER_HOUR`)。Upstash Redis を設定すればインスタンスをまたいで数え、なければサーバーのメモリで数える(README の「スパム・乱用・費用対策」)。
- ボット対策:Cloudflare Turnstile を設定すれば、送信時のトークンを入力の検証のあとに確かめる(確認できなければ 403)。

### 個人情報の扱い

- ログには個人情報を出さない。送信の失敗は送信先の名前とHTTPステータスだけを出す(WebhookのURLも出さない)。
- Slack に送るときは `<!channel>` などの制御文字を無効にする(入力で全員に通知を飛ばされないように)。
- 同意欄から `NEXT_PUBLIC_PRIVACY_POLICY_URL` のページへリンクする(別タブ)。

## 構造化出力とフォールバック(AIレポート)

SDK(`@anthropic-ai/sdk` 0.135)の `BetaMessageStream` は、応答の終わり(`message_stop`)で `parse` 付きの出力形式を受け取っていると、本文の **テキストブロックを1つずつ** 解析し、1つでも失敗すると例外にする(`lib/beta-parser` の `parseBetaMessage`)。サーバー側フォールバックが生成の途中で起きると、ストリーミングでは content が `[途中までの text, fallback, 切り替え後の text]` になるため、途中までの文の解析で例外になり、切り替え後のモデルが書いた正しいレポートも失われていた(偽のSSE応答で再現を確認)。

そこで出力形式は JSON スキーマだけを渡し(`parse` を渡さない)、`extractReport` で次の順に解析・検証する。

1. 最後の `fallback` ブロックより後のテキスト(切り替え後に最初から書き直した場合、出力前の切り替え)
2. すべてのテキストをつなげたもの(切り替え後のモデルが続きを書いた場合。ストリーミングでは途中までの文が続きの文脈として渡される)

`stop_reason` が `refusal`(フォールバック先も辞退)や `max_tokens`(途中切れ)のときは、解析エラーではなく理由のわかる例外にして標準レポートに切り替える。
