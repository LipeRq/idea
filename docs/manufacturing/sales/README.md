# 見積アシスト(仮称) 営業資料一式

製造業向けAIエージェント「見積アシスト」(引き合い対応・見積作成)を、中小〜中堅の部品加工業(従業員20〜100名程度)の社長・工場長・営業責任者に紹介し、診断 → PoC(試験導入)→ 本導入へ進めるための資料です。

- 元になった資料:[use-cases.md](../use-cases.md)(業務の選定、5章の設計・価格の仮説・KPI・リスク、6章の差別化)、[quote-assist-design.md](../quote-assist-design.md)(技術設計)、[apps/quote-assist/README.md](../../../apps/quote-assist/README.md)(MVPの動かし方と制約)
- デモ画面のスクリーンショット:[../demo/screens/](../demo/screens/)(デモ担当の資料。架空の会社「しらかば精工」の合成データ)
- **資料の中の効果と価格はすべて仮説です。** 見積アシストの導入実績はまだありません。

## 2. 営業の流れと使う資料

| 段階 | 目的 | 使う資料 | 当社がすること |
|---|---|---|---|
| 1. 初回の接触 | 興味を持ってもらう | one-pager | 無料診断(Webの診断ツールと面談)に誘う |
| 2. 初回の面談(60〜90分) | 今の見積業務とデータの状況を知る | hearing-sheet(初回の15問)、case-study-demo、デモ画面(5分。Salesforceを使っていない会社は場面10を飛ばす) | 聞き取り、デモ、データの整い具合(レベル0〜3)の判定 |
| 3. 提案 | 進め方と費用の目安に合意する | proposal-template、pricing の7章、faq-objections(答え方の準備) | 課題の整理、費用対効果の試算、NDAの確認の依頼 |
| 4. PoCの合意 | 試験導入の範囲・合格基準・日程を決める | poc-plan | 秘密保持契約、ベースライン計測の開始 |
| 5. PoCの報告と判断 | 本導入・範囲を絞って導入・追加検証・見送りを決める | poc-plan 10章、proposal-template(本導入版に更新) | 実測値で試算をやり直し、報告する |

## 3. 現行版でできること・まだできないこと

提案書・FAQで約束してよい範囲を確かめるための表です。現行版はMVP(試作版)で、APIキーがなくても「デモモード」で全画面が動きます(apps/quote-assist/README.md「制約・未実装」、quote-assist-design.md 9章)。

### 3.1 できること(デモで見せられる)

| 機能 | 補足 |
|---|---|
| 引き合いメール本文の貼り付けと図面PDF(3ファイルまで)の登録 | |
| 図面・メールからの項目の読み取り(確からしさ・根拠の位置つき)と、手での修正 | APIキーがあればClaudeが読み取る。デモモードではサンプル図面の固定結果を表示し、それ以外の図面は手入力になる |
| 必須項目の不足・矛盾のチェック、確認事項と確認メールの案 | |
| 過去案件からの類似検索と警告(赤字の可能性・価格での失注・不具合) | 合成データの過去案件200件。形状(3D)での検索はしない |
| 工程ごとの工数の案 | AIは似た過去案件の実績を根拠に示す。AIなし・失敗時は類似案件の実績から計算 |
| 見積の計算(材料・加工・段取り・外注・特急・管理費・利益・端数)、数量段階別の単価、標準リードタイム、確認ポイントの警告 | 単価表のファイルを差し替えると計算が変わる |
| 修正・承認と修正の記録 | 未確認の項目が残ったまま承認するには確認のチェックが必要 |
| 見積書のプレビュー(ブラウザの印刷でPDF保存)と回答メールの案 | 送信は人が行う |
| Salesforceへの商談+見積の登録(一方向) | モックで動作。本番の接続は環境変数がそろったときだけ有効 |
| 計測(処理時間・トークン数・概算費用・登録から承認まで・工数の案の採用率)、正解データとの照合(`npm run eval`) | 照合はデモ用の3件・9項目の正解率と確認事項の再現率だけ(PoC用の拡張は3.2) |

### 3.2 まだできないこと(約束しない。聞かれたら「今後の対応」または「持ち帰り」)

| 項目 | 状態 |
|---|---|
| 認証・権限管理 | なし。**お客様の実データを扱う前に、保存先・アクセス制限・認証を用意する必要がある** |
| 実際のAIでの読み取りの正確さ・処理時間・費用 | 未計測(PoCで測る) |
| Salesforceの実際の組織への接続 | 未検証。見積品目(QuoteLineItem)は作らず、明細は見積の説明欄に入れる |
| データのCSV/Excelでの書き出し | 未実装(提案書・FAQでは「お渡しする」と書いているため、提供開始までに用意する) |
| 国内での処理(Amazon Bedrock)、データを保存しない契約(ZDR)、専用環境 | 設計上の差し替え点のみ。未実装 |
| 見積書のExcel出力、仕様書PDFの要求事項の抜き出し、受注・失注結果の取り込み、過去図面の一括取込、保存期間の設定 | 未実装 |
| kintone・生産管理DBとの連携、メールボックスの監視・自動取込 | 次の段階 |
| PoC用の評価(お客様のデータの読み込み、希望納期・検査書類の照合、確信度別の誤り、類似検索の的中率、不要な確認事項の数) | 未実装(poc-plan 4章で使うため、PoC開始までに用意する) |
| MCPでの機能の切り出し、修正の記録に「誰が直したか」を残すこと(ログイン後) | 未実装(構想。FAQ では「構想」「予定」と書く) |
| 図面上の位置の強調表示、祝日・生産負荷を考えた納期 | 未対応(根拠は「ページ・位置の説明・原文の引用」で示す) |

### 3.3 設計としてやらないこと

見積の自動送信、AIによる値付け(利益率・値引き)、3D形状の解析、装置一式・組立品の見積、生産負荷を踏まえた納期の確約、多言語対応(use-cases.md 5.5)。

## 4. 書き方・話し方の共通ルール

| ルール | 具体的には |
|---|---|
| 仮説は仮説と書く | 作業時間の短縮・価格・回収期間には「仮説」「試算」「目安」を付け、根拠(use-cases.md の節番号・出典番号・計算式)を添える |
| 実績のないことを事実のように書かない | 「導入事例」ではなく「想定事例(デモシナリオ)」。デモの会社・人物・図面・数値は架空と明記する |
| 誇大な表現を使わない | 「必ず」「完全自動」「100%」「絶対に」は使わない。言い換えは faq-objections.md 9章 |
| AIは誤ることがあり、最終判断は人 | 「読み取りと文章はAI、計算と判定はプログラム、最終判断と送信は人」を毎回伝える |
| 実在の企業・人物の名前を使わない | 比較対象の製品は出典番号で参照し、相手を悪く言わず「範囲の違い」として説明する |
| 出典は原典で確かめる | 出典番号(S○)は use-cases.md の出典表(アクセス日 2026-10-18)。「要原典確認」の数値は社外に出す前に原典で確認する |
| 社内メモを消してから渡す | 各資料の「社内メモ」の囲みと、【】の未記入欄を残したまま社外に出さない |
| 社外の資料に社内資料の名前を書かない | 社外向けの本文には、use-cases.md などの社内資料名・リポジトリのパス・社内専用資料(pricing、faq-objections)へのリンクを書かない。根拠は社内メモに書き、本文では原典の名前とURL、または「当社の仮説」と書く |
| 費用対効果は条件と一緒に伝える | 削減額だけでなく回収期間も示し、「月60件未満では回収が難しい試算」を隠さない(pricing.md 4.3) |

## 5. 埋める欄・決めることの一覧

### 5.1 どの資料にも共通の差し込み欄

| 差し込み欄 | 入れるもの | 主な資料 |
|---|---|---|
| 【自社名】【担当者名】 | 会社名(未定のため差し込み欄)、担当者名 | 全資料 |
| 【電話番号】【メールアドレス】【WebサイトURL】【無料診断のURL】 | 連絡先 | one-pager |
| 【○社】【○年・○社】 | Salesforce導入・運用支援の実績(社数・年数)。書ける範囲で | one-pager、faq-objections Q15・Q23 |
| 担当者欄の【経歴】【製造業との関わり】【ひとこと】 | 担当者のプロフィール。製造業の経験がなければ、そう分かる書き方にする | one-pager「担当者」、faq-objections Q24 |
| 【顧客名】【2026年○月○日】【第1版】 | 提出先・日付・版 | proposal-template、poc-plan、hearing-sheet |

### 5.2 案件ごとに埋めるもの

| 資料 | 埋めるもの |
|---|---|
| proposal-template | 2章の課題、3章のヒアリング結果(数値と実測/推定の区別)、5章の導入範囲、6章の日程、7章の体制、8章の費用(pricing.md の価格表から選ぶ)、9.2の試算の件数と時間単価 |
| poc-plan | 期間・費用、定例の曜日、対象データの期間、正解データの件数、受け渡し方法と保存先、合格基準(キックオフで決める)、削除の期限、判断する方 |

| 11 | お客様の取引先にAIの扱いを説明するための書面の様式 | faq-objections Q5 |

### 5.4 提供開始(実データのPoC)までに用意が必要なもの

| 項目 | 理由 |
|---|---|
| 認証(少なくともBasic認証)とアクセス制限、実データ用の保存先 | 現行版は認証がなく、手元・デモ用 |
| 案件データ・単価表のCSV/Excel書き出し | 提案書・FAQで「お渡しする」と書いている |
| 実際のAIでの評価(`npm run eval`)と費用の計測 | 正確さ・費用の数値をまだ持っていない |
| Salesforceの検証環境(Sandbox)での接続確認 | 実際の組織への接続は未検証 |
| PoC用の評価の拡張(3.2) | poc-plan 4章の指標(自信のある誤り、類似検索の的中率など)を、お客様のデータで測るため |
| AIの会社側でのデータの保存期間の確認 | 公表内容が改定されているため、日数を書く前に公式の規約で確かめる |

## 6. 印刷・スライドにするとき

- どの資料も、見出し(##)ごとに1〜2ページ(スライド1〜2枚)に収まるように書いています。スライドにするときは「##」を1枚の区切りにします。
- one-pager.md は、見出しの「###」ごとに区切るとA4表裏に収まる分量です。
- case-study-demo.md の画像は [../demo/screens/](../demo/screens/) を参照しています。資料を別の場所に移すときは、画像も一緒にコピーします。
- 末尾の小さな注意書き(`<small>`)は、Markdownの表示ソフトによっては普通の文字で表示されます。注意書きは消さずに残します。
