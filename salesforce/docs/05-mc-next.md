# 05. Marketing Cloud Next(MC Next)の設計と移行の方針

MCE を今すぐ置き換えるのではなく、**Data 360 とのつながりが強い施策から MC Next で試し、効果と運用を確かめてから移す**方針にします。

> MC Next の機能はリリースごとに増えています。下の比較は設計の判断に効くところだけを書いたもので、実装時は最新のリリースノートと組織の画面で確かめます。

## 1. MCE と MC Next の違い(設計に効くところ)

| 観点 | MCE(現行) | MC Next | 設計への影響 |
|---|---|---|---|
| データの持ち方 | データエクステンションにコピーして使う | Data 360 のデータをそのまま使う | MC Next ではコピーと同期の処理が減る。セグメントの定義が 1 か所になる |
| 施策の組み立て | Journey Builder | フロー(Salesforce のフローの仕組み) | Sales Cloud のフローに慣れた人が扱いやすい。MCE のジャーニーとは作り直しになる |
| 個別化の書き方 | AMPscript・SSJS | 差し込み項目・条件つきの内容(Data 360 のデータを参照) | **AMPscript・SSJS の資産はそのままは移せない**。棚卸しが必要 |
| 即時性 | API イベントで即時に入口に入れる | Data 360 のイベント(Web の行動など)を起点にできる | カゴ落ちのような「行動の直後」の施策に向く |
| AI | 件名の最適化など | エージェントによるキャンペーンの作成支援など | 作成の手間は減るが、法令の確認と人の承認は残す |
| 運用する人 | MCE の専門知識が要る | Salesforce の管理者の知識の延長で扱える部分が多い | 体制(誰が運用するか)も移行の判断に入れる |

## 2. 試験する施策:カゴ落ち

| 項目 | 内容 |
|---|---|
| 入口 | Data 360 の S7(カートに入れて 1 時間以内に購入なし。Web の行動のストリーミング) |
| 流れ | 1 時間待つ → 購入の有無を確認 → カートの商品を差し込んだメール → 24 時間後にまだ未購入なら 1 通だけ追いかける |
| 頻度の上限 | 1 人 7 日に 1 回まで |
| MCE との調整 | 直近 24 時間に MCE から販促メールを受け取った人は外す(Data 360 の Email Engagement で判定)。**2 つの配信ツールを並べて使う間は、送りすぎの判定を Data 360 に置く** |
| 対照群 | 対象の 20% には送らず、購入率を比べる |
| 成功の条件 | 対照群より購入率が高く、配信停止率が販促メールの平均を超えない |

カゴ落ちを選んだ理由:

- Data 360 の Web の行動を起点にするので、MC Next の良さ(Data 360 のデータをそのまま使える・行動の直後に動ける)が出やすい
- MCE に既存のカゴ落ちの仕組みがなく、移行ではなく「新しい施策」として始められる(失敗しても既存の売上を壊さない)
- 対照群を作りやすく、2〜4 週間で結果が読める

## 3. 移行の順番の決め方

ジャーニーごとに次の観点で点を付け、点の高いものから移します。

| 観点 | 高い(移しやすい・移す価値が高い) | 低い |
|---|---|---|
| データの所在 | Data 360 のデータだけで完結する | MCE の DE や SQL に強く依存する |
| AMPscript・SSJS への依存 | 差し込みと条件分岐くらい | 複雑なロジック・外部 API の呼び出し |
| 即時性の必要 | 行動の直後に送りたい | 毎日・毎週で十分 |
| 止まったときの影響 | 小さい | 売上・法令に直結する |

| 施策 | データの所在 | AMPscript 依存 | 即時性 | 影響 | 判断 |
|---|---|---|---|---|---|
| カゴ落ち(新規) | 高 | 高(新しい施策なので依存なし) | 高 | 高(既存の売上を壊さない) | **最初に試す** |
| J4 法人窓口の案内 | 高 | 高 | 低 | 高 | 2 番目 |
| J3 休眠予備軍 | 高 | 中 | 低 | 中 | 3 番目 |
| J2 2回目購入の後押し | 中 | 中(おすすめ) | 低 | 中 | おすすめを Data 360 で作れるようになってから |
| J1 ウェルカム | 低(EC の API イベントが入口) | 低(クーポンの ClaimRow) | 高 | 低(2 回目購入の柱) | 最後 |
| 配信設定ページ | — | 低(SSJS) | — | 低(法令) | 同意の扱いを決め直してから |

## 4. AMPscript・SSJS の資産の棚卸し

| 今の使い方 | MC Next での置き換えの方向 |
|---|---|
| 姓の差し込みと空のときの代わり | 差し込み項目と既定値 |
| 好きな茶の種類で文面を変える(`IF`) | 条件つきの内容 |
| おすすめ商品(`LookupOrderedRows`) | Data 360 で 1 人ずつのおすすめを持たせて参照する(作る場所を MCE の SQL から Data 360 に移す) |
| クーポンの割り当て(`ClaimRow`) | 割り当ての仕組みを別に用意する必要がある(移行の最後にする理由) |
| 配信設定ページ(SSJS) | 同意の管理を Data 360 側に寄せて作り直す |

棚卸しは「何をしているか」で分けます。コードを 1 行ずつ移すのではなく、目的ごとに置き換え先を決めるほうが、移行後に保守しやすくなります。

## 5. 並べて使う間の注意

| 注意点 | 対応 |
|---|---|
| 配信停止の状態 | どちらで停止しても、もう一方で送らない。正は Data 360 の同意の状態にし、両方がそれを見る |
| 送りすぎ | 送信の履歴を Data 360(Email Engagement)に集め、両方の除外条件に使う |
| 送信のドメインと評判 | MC Next でも同じ認証設定(SPF・DKIM・DMARC)。送る量を少しずつ増やす |
| 効果の比べ方 | 同じセグメントを無作為に分けて、MCE と MC Next で同じ内容を送る期間を設ける |
| AI による作成支援 | 作られた文面・セグメントは、法令の確認と人の承認を通してから使う |
